## Summary

`dsh-opencharly` — OpenCharly's native DeepSeek Harness plugin, the artifact requested in
opencharly/opencharly#420 and authorized there by the operator (scope: all three seams; public;
MIT; **no host wiring in this change** — producer-first via `pod-dsh`).

A DSH plugin is a host-profile dependency rather than a repo file (`AGENTS.md` Part II rule 5 keeps
harness *config* at the umbrella root), so this repo is installed by commit into `$DSH_HOME` exactly
as `dsh-github`, `dsh-git-worktree` and `dsh-workspace-enhancement` already are.

It provides the three things a DSH session cannot wire from config:

1. **Git gates (closes W2).** A `tools/pre-execute` listener that recognizes a `git commit` /
   `git push` tool call and BLOCKS it by delegating to the repository's OWN gates,
   `.claude/hooks/pre-commit-gate.sh` / `pre-push-gate.sh`. No gate policy is re-implemented here
   (R3): the scripts read `{"tool_input":{"command":...}}` on stdin and exit 2 with the reason on
   stderr. A compound `git commit && git push` runs **both**, push first — passing the commit gate
   says nothing about the push.
2. **SOUL injection (closes W6).** A `systemPrompt` section carrying the project-root `SOUL.md`,
   read fresh at every prompt assembly. It refuses to inject outside an umbrella checkout (guarded
   by the `.claude/hooks/pre-push-gate.sh` marker), matching `.reasonix/soul-inject.sh` — one DSH
   profile serves every project on the machine.
3. **Session-start watch auto-arm.** A `session/created` listener arming the org's canonical
   `marketplace/scripts/gh_watch.sh` from `.dsh/watch.items` as a background JOB, so the session
   starts watching with nobody arming it and the job's own settlement is the wake. It arms once per
   checkout while a watcher is live, and re-arms for a later session.

Also in this PR: `package.json` (no build step, **no runtime dependencies**), `cordis.patch.yml`,
`lib/index.d.ts`, `.github/workflows/ci.yml` (Node 22 + 24), `CHANGELOG/README.md`.

## R1 finding from this PR - the CI command was version-dependent (found by CI, fixed here)

The first head shipped `node --test test/`. It **passed on Node 26** (the author's runtime) and
**failed on BOTH matrix legs in CI** (Node 22 and 24):

```
Error: Cannot find module '/home/runner/work/dsh-opencharly/dsh-opencharly/test'
  code: 'MODULE_NOT_FOUND'
```

- **Mechanism:** a positional *directory* relies on the runtime's own test-file discovery. Node 26

- **Missed control:** the local proof ran on the author's Node only, and the CI matrix - the one

  tree. That claim was false when it was written; this section exists because of it.
- **Root fix:** the shell-expanded file pattern `test/*.test.js` is now used in the workflow, the
  `package.json` test script and both README occurrences, so every supported runtime is handed

  that exact command locally, and the CI matrix on the new head was the arbiter. The tree now

### R1 finding from the fresh head — an unhandled stdin EPIPE (found by CI on Node 22, fixed)

The `exit 3` fixture exposed a **real defect in `runGateScript`, not a test bug**: a gate script that
exits WITHOUT reading stdin makes the stdin write fail with `EPIPE`, and stream errors are emitted
**asynchronously**, so the `try/catch` around `stdin.end` never sees it. With no `error` listener
that becomes an `uncaughtException` in the HOST process — a broken gate script could take the
session down. CI failed on **Node 22** with `write EPIPE` while **Node 24** (and the author's Node 26)
passed, so it is a genuine runtime difference, not a flake. Fixed by attaching
`child.stdin.on('error', ...)`; the child's `close` handler owns the outcome. This is precisely the
class of defect B12 demanded coverage for, and the new coverage found it on the first CI run.
